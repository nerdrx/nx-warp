# fuzz/ — fuzzing and sanitizer infrastructure

Phase 1 exit criterion (PAPER 3.9): **24 hours of clean fuzzing on the
reference decoder.** This directory is what produces that number, plus the
targets for the transport and the warp predictor that the same criterion will
apply to in Phase 2.

Findings from the runs so far are in [FINDINGS.md](FINDINGS.md). Permanent
reproducers live in `regressions/<target>/` and run on every push.

```
fuzz/
  <target>.cpp          one harness per target: LLVMFuzzerTestOneInput plus a
                        structure-aware LLVMFuzzerCustomMutator
  common/nxfuzz.h       shared scaffolding: RNG, byte helpers, bit fields
  common/nxfuzz_main.cpp  the regression runner's main(), linked into *_replay
  common/nxvc_stream.h  parse/mutate/serialize model of the v1 bitstream
  common/nxt_wire.h     the same for the transport datagram and feedback packet
  corpus/<target>/      seed corpus, checked in, generated by tools/gen_corpus.py
  regressions/<target>/ minimized reproducers, permanent, replayed by CTest
  dict/                 libFuzzer dictionaries
  tools/gen_corpus.py   regenerates corpus/ from tests/vectors/ + a generator
  tools/run_campaign.sh runs every target for N seconds, used by CI and locally
  oss-fuzz/             build.sh / Dockerfile / project.yaml skeleton
```

## Targets

| target | under test | invariants beyond memory safety |
|---|---|---|
| `nxvc_decode_fuzz` | the whole reference decoder, header to pixels | consumed bytes never exceed the input; a rejected header leaves the decoder reusable; output-plane guard bytes intact |
| `nxvc_headers_fuzz` | stream header, TLV area, tool mask, frame headers only | every SYNTAX.md §2 and §3.1 constraint actually holds on an accepted header |
| `nxvc_rans_fuzz` | interleaved rANS + the coefficient syntax machine | no write outside a coding unit; every decoded level inside the ±32767 the escape cap guarantees |
| `transport_depacketize_fuzz` | `nxt::Receiver` on hostile datagrams | delivered tiles are inside the grid and inside the plaintext they came from |
| `transport_rs_fuzz` | GF(256) Reed–Solomon and the FEC group builder | any *k* of *k+m* blocks recover byte-identically; fewer than *k* never claims success |
| `transport_feedback_fuzz` | the feedback packet parser | 1..3 band records; a decoded packet re-encodes and re-decodes identically |
| `warp_tile_fuzz` | `nxvc::warp::warp_tile` and the integer primitives | no write outside the 64×64 tile; every sample in `[0, max_value]` |

Each target is guarded in `CMakeLists.txt` on the component library existing,
so this directory never breaks configure while components are still landing.

## Build

Every harness builds two ways.

**Regression runner — always built, any compiler, no libFuzzer:**

```sh
cmake -S . -B build -G Ninja -DNXWARP_BUILD_VK=OFF
cmake --build build --parallel 4
ctest --test-dir build -R '^fuzz\.'
```

That gives `build/bin/<target>_replay`, registered as `fuzz.<target>.replay`.
It replays `regressions/<target>/` and `corpus/<target>/` and then runs 400
rounds of the custom mutator, so a mutator that writes past `max_size` fails
CI even where clang is not installed.

**libFuzzer — needs clang:**

```sh
san="-fsanitize=undefined -fno-sanitize-recover=undefined -fno-omit-frame-pointer -g"
cmake -S . -B build-fuzz -G Ninja \
  -DCMAKE_C_COMPILER=clang -DCMAKE_CXX_COMPILER=clang++ \
  -DCMAKE_BUILD_TYPE=RelWithDebInfo \
  -DNXVC_FUZZ=ON -DNXWARP_FUZZ=ON \
  -DNXWARP_SANITIZER=address \
  -DCMAKE_C_FLAGS="$san" -DCMAKE_CXX_FLAGS="$san" \
  -DCMAKE_EXE_LINKER_FLAGS="-fsanitize=undefined" \
  -DNXWARP_BUILD_VK=OFF -DNXWARP_BUILD_TOOLS=OFF
cmake --build build-fuzz --parallel 4
```

`NXWARP_FUZZ=ON` is not optional in practice: it is what puts
`-fsanitize=fuzzer-no-link` on the *component* libraries. Without it libFuzzer
gets no coverage feedback from the code under test and degenerates into random
testing. `fuzz/CMakeLists.txt` warns if you forget.

UBSan is added through `CMAKE_*_FLAGS` rather than by asking for
`NXWARP_SANITIZER=address+undefined`, because that preset also switches on
`-fsanitize=integer`, whose `implicit-conversion` and `unsigned-shift-base`
checks fire on well-defined code — including inside libstdc++. See FINDINGS.md
F4. The module's own flags are appended *after* `CMAKE_CXX_FLAGS`, so a
`-fno-sanitize=` there cannot undo them; narrowing has to happen this way round.

## Run

```sh
# every target, five minutes each, four workers
fuzz/tools/run_campaign.sh "$PWD/build-fuzz" /var/tmp/nxfuzz 300

# same, but out of the way of whatever else the machine is doing:
# SCHED_IDLE + nice 19 are the default, NXFUZZ_CPUS adds the pinning
NXFUZZ_CPUS=12-15 fuzz/tools/run_campaign.sh "$PWD/build-fuzz" /var/tmp/nxfuzz 300

# one target, by hand
build-fuzz/bin/nxvc_decode_fuzz /var/tmp/corpus \
    -dict=fuzz/dict/nxvc.dict -max_total_time=1200 \
    -workers=4 -jobs=4 -rss_limit_mb=4096 -timeout=25 -max_len=65536
```

`run_campaign.sh` copies the seed corpus and the regression inputs into a
working directory under the *output* tree; it never writes back into
`fuzz/corpus/`, which stays a curated, small, checked-in set.

Scheduling knobs (`NXFUZZ_CPUS`, `NXFUZZ_NICE`, `NXFUZZ_IDLE`, `NXFUZZ_WORKERS`)
are all probed before use, so the same script runs unchanged on a workstation
with 32 cores and on a 2-core CI runner where `taskset -c 12-15` would fail.

For the 24-hour Phase 1 run, give one target the whole machine rather than
splitting the budget:

```sh
fuzz/tools/run_campaign.sh "$PWD/build-fuzz" /var/tmp/nxfuzz-24h 86400
```

## Reproduce

```sh
# libFuzzer build: one input, symbolized
build-fuzz/bin/nxvc_decode_fuzz fuzz/regressions/nxvc_decode_fuzz/F3-....bin

# no clang: the plain runner reproduces the same crash
build/bin/nxvc_decode_fuzz_replay --timeout 30 path/to/input

# minimize before filing
build-fuzz/bin/nxvc_decode_fuzz -minimize_crash=1 -runs=100000 \
    -exact_artifact_path=fuzz/regressions/nxvc_decode_fuzz/Fn-short-name.bin \
    crash-<sha1>
```

Name a committed reproducer `F<n>-<what-it-hits>.bin` so the file says which
FINDINGS.md entry it belongs to.

When no libFuzzer build is available, the regression runner can still produce
reproducers: `--dump-dir DIR` writes each mutated input immediately before
executing it, so after a crash the newest file in `DIR` is the input.

## Adding a target

1. Write `fuzz/<name>_fuzz.cpp` with `LLVMFuzzerTestOneInput`. Put every
   invariant you can afford in it — a fuzz target that only checks "did not
   segfault" finds an order of magnitude less than one that checks what the
   spec actually promises. Use `__builtin_trap()` for a hard invariant (memory
   safety, a length that must hold) and `nxf::note_soft_violation("...")` for a
   soft one (the spec and the implementation disagree but nothing is read out
   of bounds), so a soft violation does not mask every memory bug for the rest
   of the run. `NXFUZZ_VERBOSE=1` prints the first occurrence of each.
2. Add a `LLVMFuzzerCustomMutator`. Reuse `common/nxvc_stream.h` or
   `common/nxt_wire.h` if the input is one of those formats; otherwise mutate a
   typed parameter prefix as fields and the tail with `mutate_bytes`.
3. Register it in `fuzz/CMakeLists.txt`:
   `nxfuzz_add_target(<name>_fuzz LIB <component target> INCLUDE <dirs>)`.
4. Add seeds to `tools/gen_corpus.py` and rerun
   `cmake --build <build> --target nxfuzz-corpus`.
5. Add its name to the target list in `tools/run_campaign.sh` and
   `oss-fuzz/build.sh`.

## Mutator design

The reason for the custom mutators is measurable. The NX Warp stream header is
64 bytes with a magic, a version, a tool mask that must be a subset of what the
decoder implements, and a width and height that must be even and in range. A
byte-level mutator that lands anywhere in those 64 bytes usually produces a
stream that is rejected in the first hundred instructions, so essentially the
whole budget is spent measuring the header check. The same is true of the
transport, where the directory lengths must sum to the plaintext length or the
datagram is discarded whole, and of the rANS payload, where the first
`4 × active_lanes` bytes are per-lane initial states that must each be ≥ 2¹⁶.

Each mutator therefore works on a **model**, not on bytes:

* `common/nxvc_stream.h` parses a stream into
  `Stream → Frame* → Row* → Tile*`, mutates one *field* — a header field
  drawn from its legal range and from the values just outside it, a tile-header
  bit field, a payload, a whole row or frame added, duplicated or dropped —
  and then re-serializes, **repairing** every length the change invalidated:
  `ext_len`, `frame_bytes`, `tile_count`, `payload_len`.

* `common/nxt_wire.h` does the same for the 24-byte datagram header, the tile
  directory and the feedback packet's band records and bitmaps. It follows the
  **v2** bit layout of TRANSPORT.md §2 and §3.1 (decision D19 moved `ref_delta`
  and `tile_class` out of the header into the directory and added `fec_class`
  and `fec_m`); if that layout changes again, this header and `dict/nxt.dict`
  are the two places to update, and the seeds in `tools/gen_corpus.py` the
  third.

Repair is deliberately not total. A separate family of *desync* mutations
breaks exactly one length field on purpose — `frame_bytes` set to 39,
`tile_count` one more than the tiles present, an RLE `nruns` that promises more
bytes than the packet carries — because those length checks are precisely the
code that must never read out of bounds. Truncating the finished serialization
at a random offset is a further mutation, and it is the cheapest way to hit
every truncation path at once.

When the input does not parse at all, the mutator synthesizes a fresh
well-formed stream instead of mutating noise. That is what stops a corpus from
drifting out of the interesting part of the space over a long run.

Two more details worth keeping:

* **`transport_depacketize_fuzz` seals what it feeds.** A datagram is
  authenticated with an AEAD over the header as associated data, so random
  bytes fail the tag check and the harness would only ever measure the AEAD.
  The input is treated as `header(24) || plaintext`, and the harness re-seals
  the plaintext under the receiver's own subkey before feeding it. The raw,
  unsealed bytes are fed as well, on every input, so the auth-failure path
  keeps its coverage.

* **`nxvc_rans_fuzz` repairs the lane states.** The mutator ORs `0x00010000`
  into each initial state most of the time, so the payload gets past the ≥ L
  check and into the symbol loop, while the low bits stay under the fuzzer's
  control.

The dictionaries in `dict/` are the other half: magic numbers, tool masks, the
`kDenMin`/`kDenMax` denominators, `tile_first` values on and just past the
68×34 grid, and the reserved bit patterns that must be refused.

## CI

| workflow | job | what it does |
|---|---|---|
| `sanitizers.yml` | `asan+ubsan` | full build + ctest under ASan and UBSan, on every push and PR |
| `sanitizers.yml` | `tsan` | the same under ThreadSanitizer (which cannot be combined with ASan) |
| `sanitizers.yml` | `fuzz-smoke` | replays every reproducer, then 60 s of libFuzzer per target |
| `nightly.yml` | `fuzz` | replays the reproducers, then 20 minutes of libFuzzer per target, and uploads crashers |

## OSS-Fuzz readiness

`oss-fuzz/` holds a `build.sh`, `Dockerfile` and `project.yaml` that are
correct as written and can be dropped into `projects/nx-warp/` of the OSS-Fuzz
repository. The project has **not** been submitted, so nothing exercises those
files directly — but everything they depend on is exercised: the same targets,
seed corpora and dictionaries are built and run by both workflows above.

What is already in place for onboarding:

* one `LLVMFuzzerTestOneInput` per target, no `main()` of its own in the
  libFuzzer build;
* no dependency on the source tree at runtime — every target reads only its
  input buffer, and the transport targets use the built-in `NullAead`, so
  `-DNXVC_TRANSPORT_OPENSSL=OFF` leaves the build with no external dependency;
* seed corpora and dictionaries checked in, packaged as
  `<target>_seed_corpus.zip` and `<target>.dict`;
* bounded work per input (picture area, frame count, block length and
  reference-image size are all capped in the harness), so no input is a
  timeout by construction;
* MSan-compatible harnesses: every buffer handed to a component is either
  `memset` or fully written before use.

What still has to happen: a public repository URL in `project.yaml` and the
`Dockerfile`, a real `primary_contact` list, and the upstream PR.
