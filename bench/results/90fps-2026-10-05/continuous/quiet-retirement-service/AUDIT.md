# Quiet retirement service review

Reviewed source `wt-pyrowave-probe` at `85cbc286`; read-only. No session/device/runtime activity.

The proposed wrapper is scoped correctly if it preserves `next_nack_deadline()` and is used only by the existing ASTC poll path. Poll timeout construction already runs under `decoder_mutex` shared lock on the network thread (`client/scenes/stream_network.cpp:70–77`); post-poll service uses the same lock and thread (`:79–87`). `display_period_ns()` is a relaxed atomic load (`client/scenes/stream.h:742–746`), and the scene is weakly held by each accumulator (`client/decoder/shard_accumulator.h:64,112`). Locking the weak scene for the period read adds no new long-lived ownership. The property is sampled in the accumulator constructor and is Android-only; deadline retirement defaults off on other platforms and remains opt-in on Android (`client/decoder/shard_accumulator.cpp:63–72`, header `:115`). Recovery polling is independently default-off (`client/scenes/stream_network.cpp:41–50`).

Retirement gating should mirror `pump()` exactly: feature enabled, scene available with positive display period, front received timestamp positive, no clock rollback (`now >= first_received`), front nonempty and incomplete, and a newer complete frame exists (`client/decoder/shard_accumulator.cpp:222–237`; `client/decoder/frame_window.h:31–37,154–158`). Validate multiplication and absolute-deadline addition separately: the current predicate safely uses elapsed subtraction and rejects periods above `INT64_MAX/2`; a `first_received + 2*period` deadline also needs `first_received <= INT64_MAX - 2*period`. Missing/incomplete cases must continue to use the unchanged NACK deadline. If the display period is still zero, `pump()` itself has no retirement deadline, so the wrapper must not invent one.

Calling `pump(now)` before `try_nack(now)` from the opt-in poll service is semantically sound: an already-expired frame is retired and feedback emitted before spending another request round; the subsequent `try_nack()` still services remaining eligible frames. `pump()` already runs from shard and parity visitors on this same network thread while the decoder-list shared lock is held (`client/decoder/shard_accumulator.cpp:150–188,190–238`), so this adds no new caller thread or lock mode. Do not call pump on disabled/non-ASTC paths. The retirement poll deadline must be combined with, not replace, the earliest NACK deadline so either event can wake the loop.

Minimum focused check: use the production accumulator/window methods or extracted exact methods with virtual time for both orderings (retirement earlier than next NACK, and NACK earlier than retirement), plus disabled property, zero/negative period, rollback, overflow, no-newer-complete, complete front, and already-retired feedback. Confirm a deadline wake retires only the stale front, then NACKs remaining holes, and never requests the just-retired frame. Source review finds no lifetime or default-activation blocker; timing and live XR effects remain unmeasured.

## Review of pending source patch

The actual patch follows this design and has no must-fix issue from source review. `next_poll_deadline()` preserves `next_nack_deadline()` and returns the earlier deadline only for an enabled ASTC deadline with a nonempty/incomplete front, newer complete frame, live scene, valid positive timestamp/period, and safe deadline arithmetic (`shard_accumulator.cpp:119–137`). `process_packets()` combines that result with the existing 100ms cap; `poll_nacks()` pumps before retrying NACKs (`stream_network.cpp:70–86`, `shard_accumulator.cpp:139–149`). A just-retired front is therefore removed before `try_nack()` can request it. Empty front / complete front / invalid or changing period returns the existing NACK deadline or none; after `pump()` advances to an empty front, the next supplier falls back to the 100ms cap, so no zero-time spin. Period is sampled again during `pump()`; if it increases between scheduling and service, pump declines retirement and the next timeout is recomputed. If it decreases, the existing 100ms maximum bounds how late a newly earlier deadline can be noticed. The existing 0ms overdue timeout correctly makes a known due event immediate and is recomputed after service.

This remains a source review only; the earlier test recommendation still applies before integration is treated as validated.
