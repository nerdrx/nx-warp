# Tiny-peak jitter hazard

At source `412a2bfe`, each admitted BBR delivery sample resets `bandwidth_peak_since` whenever its rate is strictly greater than the previous max ([bitrate_controller.cpp](https://github.com/nerdrx/wivrn-nx/blob/412a2bfe9ef54333fdc35cf9919c6443fa409909/server/driver/bitrate_controller.cpp), lines 476–85). The slowdown cohort then includes only samples timestamped at or after that point, and requires 12 samples in the two-second analysis window ([same](https://github.com/nerdrx/wivrn-nx/blob/412a2bfe9ef54333fdc35cf9919c6443fa409909/server/driver/bitrate_controller.cpp), lines 545–601; [header](https://github.com/nerdrx/wivrn-nx/blob/412a2bfe9ef54333fdc35cf9919c6443fa409909/server/driver/bitrate_controller.h), lines 192–98, 311–14).

If an otherwise stable link reports tiny upward rate jitter repeatedly, each strict new maximum can restart the cohort before it reaches 12. Generic BBR then sets `slowdown_rate` to zero until confirmation, disabling rate-only acute slowdown ([controller](https://github.com/nerdrx/wivrn-nx/blob/412a2bfe9ef54333fdc35cf9919c6443fa409909/server/driver/bitrate_controller.cpp), lines 1144–60). Loss and severe-utilisation cuts remain, so the risk is specifically missed non-acute delivery-rate slowdown while the noisy epoch never confirms. This is a source-derived risk, not observed runtime behavior.

Smallest policy option: reset the epoch only when the max improves by a quantization-aware material margin, instead of any `rate > old_peak`; derive that margin from measured timestamp/byte-rate resolution. One focused virtual test should feed >12 stable loaded samples with repeated sub-margin increases, then a rate-only slowdown below severe utilisation: require confirmation and the expected slowdown response. Pair it with one genuine material new peak to ensure the cohort restarts. Do not change code until that gate establishes both behaviors. No build, benchmark, or live-state check was run.
