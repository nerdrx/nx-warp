# Network quiet-poll source audit

Source: `wt-pyrowave-probe` at `2f53c2cb`. Read-only; no sockets, apps, XR, GPU, or device activity.

`scenes::stream::process_packets()` samples the recovery-poll opt-in once at thread start. When enabled it computes `min(100ms, nack_poll_timeout(...))`, passes that supplier to `wivrn_session::poll`, then calls `poll_nacks()` after every non-shutdown return (`client/scenes/stream_network.cpp:41–89`). Decoder-list shared locks protect deadline calculation and NACK polling. Exceptions skip that poll's NACK service and follow the existing reconnect path (`:89–102`).

There is no source evidence of an unbounded socket-drain starvation loop. `wivrn_session::poll` drains `receive_pending*()` buffers before calling the timeout supplier (`client/wivrn_client.h:295–342`), but UDP `receive_pending()` only pops the current vector; `receive_raw()` fills it with at most 20 datagrams per `recvmmsg` (`common/wivrn_sockets.cpp:349–440`). TCP `receive_pending()` consumes only complete messages already buffered by its prior read (`:564–646`). Thus queued receive work is finite per poll invocation; it does not refill the UDP vector during the drain. A due quiet deadline can wait for that buffered batch's visitor work, but sustained future arrivals do not bypass the supplier indefinitely. Each valid primary packet separately calls `steady_clock::now()` through `on_primary_received()` (`client/wivrn_client.h:306–329`, `client/wivrn_client.cpp:335–338`); no evidence here justifies removing that path-selector update.

`nack_poll_timeout()` rounds the remaining deadline up to whole milliseconds and uses a 1 ms minimum when already due (`client/decoder/nack_deadline.h:55–70`), future-deadline quantization adds less than 1 ms to the requested wait. The overdue case explicitly requests 1 ms; OS wake-up delay is not bounded by that request. Poll is capped at 100 ms. No shutdown/reconnect defect found: shutdown skips post-poll NACK work, and a thrown poll follows existing reconnect handling.

The overdue 1 ms floor is a small, real latency opportunity, not a spin guard required by the current call sequence. `next_nack_deadline()` only returns an already-due deadline after confirming missing shards; the poll requests an additional 1 ms wait, and `process_packets()` immediately invokes `poll_nacks()` (`client/decoder/shard_accumulator.cpp:75–110`, `client/scenes/stream_network.cpp:76–87`). `try_nack()` then records `nack_last` and increments `nack_rounds` before sending, so the next deadline is either cleared or moved by the 2.5 ms quiet period; it cannot remain immediately due in a tight loop (`client/decoder/shard_accumulator.cpp:300–369`). Returning a zero timeout for an already-confirmed overdue deadline would therefore remove the nominal extra 1 ms requested wait before service without causing repeated zero-time polls in the ordinary successful path. The gain is bounded and small; send exceptions still take the existing reconnect path. This merits measuring as a narrow alternative in the sibling typed-poll gate, not adding another probe here.

Existing `tests/udp_buffer_test.cpp` verifies real UDP batch ordering and buffer ownership, not the session timeout callback. A session-level loopback needs real typed loopback UDP and TCP sockets plus a no-handshake test constructor/injection seam; the public `wivrn_session` constructors otherwise perform crypto handshake and configuration setup (`client/wivrn_client.cpp:430–462`). A no-op visitor can test timeout-supplier calls and batch boundaries without XR/scene/GPU. This is an optional integration check, not evidence of a production starvation bug. A sibling gate is already covering the typed-poll loopback, so no second gate or source change is proposed here.
