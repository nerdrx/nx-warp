# Receiver repair path audit

Source snapshot: `wt-pyrowave-probe` at `85cbc286`. Read-only audit; no app, session, socket, XR, GPU, or device run.

## Actual request and reply path

With recovery polling enabled, `scenes::stream::process_packets()` asks each native ASTC accumulator for its next NACK deadline, polls the network session, then calls `poll_nacks(now)` (`client/scenes/stream_network.cpp:53–88`). `poll_nacks()` only calls `try_nack()` (`client/decoder/shard_accumulator.cpp:118–122`); ordinary shard and parity visitors call `push_shard()` / `push_parity()`, which insert, drain parity, call `try_nack()`, then `pump()` (`client/scenes/stream_network.cpp:279–300`, `client/decoder/shard_accumulator.cpp:150–188,190–219`).

`try_nack()` builds the bitmap from the actual missing-shard set, increments the round before sending, and calls the scene's `send_nack()` (`client/decoder/shard_accumulator.cpp:300–379`; `client/scenes/stream_network.cpp:512–522`). Client `send_stream()` uses primary UDP when available and selected; otherwise it uses secondary TCP or the primary control TCP socket (`client/wivrn_client.h:139–175`). The server's NACK visitor intentionally returns unless a lossy primary stream exists and video is not on secondary; it asks the compositor/encoder history for plaintext recovery blobs and sends decoded shards back through normal `connection->send_stream()` (`server/driver/wivrn_session.cpp:1047–1069`, `server/compositor/compositor.cpp:2197–2208`, `server/encoder/video_encoder.cpp:544–607`). History holds only primary-path shards and enforces age/byte/entry bounds (`server/encoder/video_encoder.cpp:1040–1048`, `server/encoder/shard_history.h:35–66,123–155`). This TCP/secondary exclusion is intentional: no repair is useful for reliable TCP delivery.

## Remaining correctness gate

The prior receiver method gate extracts `next_nack_deadline`, `poll_nacks`, and `try_nack` into a projected class; its own report says constructor, real `push_shard` / `push_parity`, `pump`, scene/network loop, and sockets are excluded (`continuous/receiver-nack-methods/README.md`). The typed poll gate separately covers socket/poll behavior, but it does not correlate an actual request to a server history hit, retransmitted serialized shard, and completed receiver frame (`continuous/network-quiet-poll/README.md`). The smallest useful next loopback is therefore one lossy-primary case with real typed UDP packet serialization on both sides: send a tiny valid frame with one known interior data shard withheld and parity insufficient, observe the actual NACK bitmap, serve that frame/index from `shard_history`, return the shard, and assert the receiver frame becomes complete with no additional NACK. Add a TCP/secondary control asserting no duplicate UDP repair. Keep test seams at scene/session send callbacks; no XR decoder/GPU is needed if completion is asserted at the actual accumulator boundary.

There is a separate conditional pump gap: `poll_nacks()` does not call `pump()`, while only `push_shard()` / `push_parity()` do. `pump()` is the only path that passes `frame_deadline_expired()` into `frame_window::drain()` (`client/decoder/shard_accumulator.cpp:118–122,184–238`; `client/decoder/frame_window.h:183–214`). That expiration requires the Android-only `debug.wivrn.nx.astc_deadline=1` property, a newer complete frame, and two display periods (`client/decoder/shard_accumulator.cpp:63–72`; `client/decoder/frame_window.h:31–37`). If this opt-in and recovery polling are both enabled, an incomplete front frame plus a newer complete frame can remain queued after traffic stops: polling advances NACK rounds but never reevaluates frame retirement. After two NACK rounds, no NACK deadline remains to wake early; the 100 ms cap alone does not pump the window. This is source-derived conditional behavior, not a reproduced defect. A focused accumulator test should construct that state, advance virtual time past two display periods, call the production polling entry, and assert whether the stale front retires and its feedback is emitted; decide explicitly whether deadline wakeups should also call `pump()`.

Prior scope: `receiver-nack-methods` already covers real parity reconstruction and two NACK rounds, while `network-quiet-poll` covers actual typed poll templates and TCP framing. Neither is an end-to-end request/reply/frame-completion test. No live latency or recovery claim follows from this audit.

## Follow-up evidence

Root subsequently ran a narrow exact-method check of `poll_nacks`, `try_nack`, `pump` and `try_submit_front`: [virtual retirement boundary](retirement/README.md). It confirms that the polling entry alone leaves the blocked window unchanged after two repair rounds; an explicit pump releases the newer frame only when the opt-in deadline is enabled. Scene, clock, decoder and feedback callbacks remain stand-ins. This does not reproduce the full Android network loop or establish a live stall duration.
