# Native ASTC UDP send audit — 2026-10-05

Audited source revision `831aafed88e16569aa09d78f2d34d812ce8a9b6c`.

The ordinary native ASTC frame path is **not batched**. `video_encoder::SendData()` sends each primary shard through `cnx->send_stream(...)` (`server/encoder/video_encoder.cpp:950-959`). The typed socket serializes into a reused thread-local packet and invokes `send_raw()` (`common/wivrn_sockets.h:374-380`); UDP reuses thread-local iovec storage and makes one `writev_with_retry()` call per datagram (`common/wivrn_sockets.cpp:476-503`). Per-shard FEC/history snapshots happen before send (`video_encoder.cpp:926-931`), and striping can route suffix shards over TCP (`video_encoder.cpp:933-948`). FEC parity sends also remain individually ordered at block boundaries (see `SENDER_BATCH_AUDIT.md`).

A production batch API already exists (`wivrn_sockets.h:382-385`, `wivrn_sockets.cpp:506-561`), backed by `sendmmsg`, but repository call-site search finds no use for video shards. It reuses iovec, message-header, and IV-counter vectors; encryption still runs once per packet and mutates serialized spans in place (`wivrn_sockets.cpp:519-550`). The source explicitly permits an unsent UDP tail (comment at line558); this is an existing best-effort policy, not a newly exercised live failure. The batch call does not retry transient errors or report a positive partial send: it returns the byte total for every requested packet even when `sendmmsg()` accepted fewer (`558-561`). By contrast, normal UDP sends use `writev_with_retry()`.

The NACK path first collects up to the existing retransmit limit, then immediately sends each cached shard unpaced on the network thread (`server/driver/wivrn_session.cpp:1049-1065`). This is the only plausible safe batch boundary because it avoids frame pacing/FEC ordering, but batching it today risks silently dropping the unsent tail on a partial syscall. The ordinary video path also has byte pacing, parity interleaving, striping, and per-send retry semantics; buffering it to batch would change those boundaries.

Prior scratch check `overnight-recovery/sender-batch-check/README.md` already exercised production typed UDP sockets on IPv6 loopback with AES-CTR, exact order/payload verification, widths 1/8/64/128, and deterministic partial-send/EINTR wrappers. It measured only about 0.07–0.10 us/datagram apparent savings at widths 8–128, without confidence intervals; at the configured 2,000 repair shards/s ceiling, the estimated upper-bound saving is about 0.2 ms CPU/s. The deterministic partial-call test showed the current batch API reports all bytes while only one datagram arrived. This is small and unsafe as-is, not evidence of a real sender bottleneck.

**Decision:** no justified send optimization or new timing gate. Do not batch ordinary ASTC shards, and do not route NACK replies through `send_many_raw()` until the partial-send/retry contract is fixed and meaningfully tested. The existing typed-socket loopback check is already the right short offscreen gate after that prerequisite; rerunning it unchanged would not alter this decision. No production files, runtime settings, or network settings changed.
