# Compositor retirement ownership (source audit)

Source checkout: `wt-pyrowave-probe`, revision `09e7951a`. Read-only; no runtime or GPU validation.

`server/compositor/compositor.cpp:787–807` moves/clears the frame and can return early; `:809–814` acquires one of two shared images. The single `cmd_pool`, `cmd`, `query_pool`, timeline semaphore and `sem_value` are compositor members (`server/compositor/compositor.h:98–108`); reset/begin of the pool and query pool happens at `compositor.cpp:838–842`, before later motion-safety checks. The one-second timeline wait is at `:1214–1227`. On timeout it marks motion data unsafe, skips query readback and motion send, then still garbage-collects at `:1253–1254`. That timeout does not itself prove the submission retired.

The proposed retirement gate needs to protect the shared command pool/query pool and any resources referenced by the prior submission. A dedicated `VkFence` attached to each successful `submit2` and polled before `acquire_image`/pool reset is the clearest separation from the existing compute-stage timeline. Set pending only after submit succeeds; clear it only after fence success. If still pending, clear/drop this frame and return before acquire/reset. Do not treat the existing timeline wait or query result as full-submit completion: its signal stage is narrower, and the bottom timestamp query precedes optional mirror work. Extending the timeline signal to `ALL_COMMANDS` may also extend downstream waits because `sem_info` is passed to encoder `present_image` (`:1181–1201`); that requires separate signal/consumer scope handling and should not be assumed equivalent.

**Serialization on the actual native multi-compositor route is established by its worker loop.** `server/driver/wivrn_session.cpp:374` passes `&self->compositor.base` to `comp_multi_create_system_compositor`. Monado starts one `thread_func` for that `multi_system_compositor` (`build-server/_deps/monado-src/src/xrt/compositor/multi/comp_multi_system.c:648, 896`); its `multi_main_loop` transfers all active clients' layers and calls `xrt_comp_layer_commit(xc, ...)` once per iteration (`:611–614`). Therefore native `layer_commit` calls through this route do not overlap each other, although IPC handlers may submit client layer data concurrently. The handlers' `global_state.lock` is only for slot bookkeeping after commit (`build-server/_deps/monado-src/src/xrt/ipc/server/ipc_server_handler.c:1377–1431`), so it is not the serialization mechanism. A pending flag/fence on this one native path can rely on worker ownership; any other direct callers of the native compositor were not established here.

Multi-client layers are copied into a stack array of compositor pointers during `transfer_layers_locked` (`comp_multi_system.c:264–275, 360–376`), then immediately passed to the native layer callbacks. The stack array itself is not retained. Its layer records live in each client's `delivered` slot; slots hold swapchain refs (`build-server/_deps/monado-src/src/xrt/compositor/multi/comp_multi_compositor.c:40–67, 973–984`) and are retired/cleared under `list_and_timing_lock` when replaced or dropped (`comp_multi_system.c:288–309`). The worker releases that lock before native `layer_commit` (`:610–614`), so concurrent client updates do not mutate the stack snapshot, but delivered-slot refs may be released on a later iteration while an earlier GPU submission is pending. Native `comp_layer_accum` stores raw `xrt_swapchain *` values in `sc_array` (`build-server/_deps/monado-src/src/xrt/compositor/util/comp_layer_accum.c:20–27, 59–93`); it does not itself retain a swapchain reference. Thus source lifetime depends on the surrounding refs and deferred-destruction path, not the layer accumulator or its stack snapshot.

Default create/import installs `really_destroy` (`build-server/_deps/monado-src/src/xrt/compositor/util/comp_swapchain.c:710–748`), which calls `comp_swapchain_teardown` (`:500–520`). `swapchain_destroy` only queues the object (`:38–47`); GC pops it and calls `real_destroy` (`:676–682`). Teardown checks per-image `use_count`, then `image_cleanup` locks `main_queue` and calls `vkDeviceWaitIdle` before destroying image views (`:277–295, 635–652`). Consequently, GC after the layer-commit timeout can block until device work retires; it does not establish premature physical destruction or a use-after-free. It is a potentially expensive synchronous cleanup path, and lifetime/image-reuse behavior outside that object-destruction path was not resolved here. Teardown also calls `device.waitIdle()` before stopping the encoder and collecting/destroying state (`server/compositor/compositor.cpp:1989–2010`), but that is shutdown-only. Monado's generic main compositor collects during session cleanup and after draw (`src/xrt/compositor/main/comp_compositor.c:170–181, 330–345`); the custom callback's post-timeout GC invokes the default destroy route described above.

The narrow recording-retirement guard has since been implemented and checked as described in the report. Before broader wait or GC changes, audit any other native callers and downstream image/mirror lifetimes. This guard leaves the existing end wait and default destruction waits intact. This source audit does not demonstrate a live fault or performance effect.
