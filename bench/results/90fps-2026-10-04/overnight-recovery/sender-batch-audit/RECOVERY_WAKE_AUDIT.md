# Recovery scheduling wake audit

## Finding

There is already a periodic wake, with no new timer required: `stream::process_packets()` calls `network_session->poll(*this, 100ms)` in a loop (`client/scenes/stream_network.cpp:34-47`). The poll watches the incoming video/stream socket, control socket, and optional secondary socket, then returns on any event or after its timeout (`client/wivrn_client.h:294-303, 342-356`). Therefore, if video shards stop but control traffic continues, it still wakes on that traffic; if all traffic stops, it wakes on the existing 100 ms timeout.

`try_nack()` is currently called only after a data-shard or parity-shard arrival, before that callback's `pump()` (`client/decoder/shard_accumulator.cpp:101-139, 155-170`). Its quiet gate is 2.5 ms and it permits at most two rounds (`client/decoder/shard_accumulator.cpp:251-330`, `client/decoder/shard_accumulator.h:168-181`). No timeout callback currently services it.

The smallest candidate is a network-thread maintenance tick immediately after each successful `network_session->poll()` return. It would iterate configured accumulators and expose a narrow `try_nack(now)` wrapper only. The same network thread already owns all accumulator mutations through `process_packets()` dispatch, and packet handlers use `decoder_mutex` shared while accessing the decoder array (`client/scenes/stream_network.cpp:237-258`; array lock comment at `client/scenes/stream.h:309`). A tick under that same shared lock would not add render-thread exclusion: render accesses also take the shared lock. Decoder reconfiguration takes exclusive ownership, so it could defer a tick briefly, as it already can defer a packet callback. Do not run `pump()` from this maintenance path; it can submit/retire frame state and is outside the NACK-only purpose.

This does **not** provide a 2.5 ms scheduler. In a quiet session, the known timeout bound is 100 ms. There is also a periodic server time-sync query routed on the stream socket: `clock_offset_estimator::request_sample()` sends at 10 ms intervals during initial sampling, then 100 ms intervals (`server/driver/clock_offset.cpp:46-56, 58-70`), and the client answers it in `stream_network.cpp:410-415`. That can wake the poll when the stream path works, but is not a stronger guarantee than the existing timeout and is not control-socket traffic. Do not shorten the poll timeout to 2.5 ms without a separate CPU/power justification.

## Test gate before considering the candidate

Use the existing actual accumulator test harness with a deterministic XR clock: insert an incomplete, NACK-eligible frame; stop injecting video/parity; advance time past 2.5 ms; invoke the proposed maintenance entry point and assert exactly one NACK, unchanged bitmap/round limit, then verify no second round before another 2.5 ms. Keep a control case proving ordinary arrival-driven NACK behavior is unchanged. Add one small loopback integration check that leaves only control traffic (and separately no traffic) after the loss: the maintenance tick must fire on the existing poll return, NACK delivery must not block the network loop, and measured wake delay may approach 100 ms. Reject the candidate for latency use if the required recovery deadline is below that bound; no faster timer is justified by this audit.

This is a small validation candidate for eventual recovery after the final missing shard has stopped arriving. It is not evidence of improved frame latency or a production recommendation. Existing stereo-age retirement/deadline experiments remain rejected in `reassembly-deadline/COHERENCE_AUDIT.md` and are unrelated to scheduling this NACK-only check.
