# Ready-wait exploratory appendix

Separate single-trial crowd tail64 experiment. The client waits briefly for a newer decoded frame before selection when the refresh would otherwise repeat. This was not promoted or default-enabled.

| wait cap | new-source FPS | app render-loop FPS | decode→selection ms | predicted runtime ms | holes |
|---:|---:|---:|---:|---:|---:|
| 0 ms | 87.30 | 89.45 | 6.30 | 41.65 | 0 |
| 1 ms | 87.18 | 89.45 | 3.83 | 39.22 | 0 |
| 2.5 ms | 87.33 | 89.44 | 4.26 | 39.79 | 0 |

Fresh-source FPS is effectively unchanged across this single trial. The approximately 2 ms derived-runtime difference may be phase variation; it is insufficient to establish a win. `predicted runtime` is a same-client-clock estimate, not photon or physical end-to-end latency.

`windows.json` contains sanitized numeric windows and citations, `summary.json` contains aggregates, and `comparison.png` is regenerated by `rebuild_report.py`. No photos, private previews, absolute source paths, or production changes are included.
