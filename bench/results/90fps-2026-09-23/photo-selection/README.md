# Direct frame selection A/B

Paired crowd tail64 runs compare the default `newest-direct` selection with the opt-in `nearest-target` experiment. The workload and transport remain separate from the ready-wait experiment; no ready-wait results are included here.

| mode | new-source FPS | app render-loop FPS | wire ms | decode→selection ms | own GPU ms | predicted runtime ms | holes |
|---|---:|---:|---:|---:|---:|---:|---:|
| newest-direct (default) | 87.00 | 89.44 | 3.30 | 5.88 | 4.19 | 41.21 | 0 |
| nearest-target (opt-in) | 89.15 | 89.46 | 3.48 | 12.28 | 4.20 | 47.72 | 0 |

Nearest-target raises fresh-source rate by about 2.15 FPS, but adds about 6.40 ms decode-to-selection and 6.51 ms to the derived first-arrival-to-predicted estimate. This is a presentation tradeoff; it is not a photon or physical end-to-end measurement. The default newest-direct mode remains the lower-latency choice in this A/B.

Values are means of independent complete 2-second window means; `p95` uses nearest-rank `ceil(0.95*n)-1`. `predicted runtime` sums wire, queue, decode, decode-to-selection, and selection-to-predicted on the client clock. `windows.json` contains sanitized numeric windows and line citations, `summary.json` contains aggregates, and `comparison.png` is regenerated by `rebuild_report.py`. No photos, private previews, absolute source paths, or production changes are included.
