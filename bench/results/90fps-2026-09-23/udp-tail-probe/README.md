# UDP tail flush probe

Standalone Linux UDP evidence for a possible burst flush marker. The probe ran independently while the fixed25 application was active; it does not measure the production application path.

The measured span is the kernel `SO_TIMESTAMPNS` difference between the earliest and latest received datagram in each frame. It is only a burst-arrival interval: it is not one-way latency, link capacity, display latency, or photon latency. Sender values are local send-loop spans and are not link-capacity measurements.

The three confirm64 trials all had zero loss: two used the recorded `delay1` setting and one used `delay500`; they must not be described as three 500 µs repeats. The separate 64 × 16 B 500 µs tail run also had zero loss. Expected counts come from the sender footer and include wholly missing frames. Burst percentiles use complete frames only, with the nearest-rank definition; loss counts cover every sent datagram.

A 64 × 16 B tail adds `64 × 16 × 90 × 8 = 0.737 Mbps` UDP payload before IP/UDP/L2 overhead, plus packet-rate and CPU cost. A 32 × 1200 B tail adds `32 × 1200 × 90 × 8 = 27.648 Mbps` payload and was lossy in this sample; it is not a recommendation. EF QoS is retained as rejected evidence because it was slower and lost packets here.

The sender traces show the 64 main 1200-byte packets taking about 0.10–0.11 ms median per local send loop, equivalent to 55.296 Mbps of main-payload arithmetic at 90 Hz. This does not establish link capacity.

`summary.json` is generated by `rebuild_evidence.py` from the raw receive/send logs and includes all `confirm0` through `confirm5` labels. The bundled `*-send.txt` logs retain sender totals. The rebuild script repairs stdout/stderr footer interleaving before parsing and checks that every sender frame is present; it needs no private fixtures. `comparison.png` is the value-labeled graph. `udp_burst.cpp` is the standalone probe source. No user images, IP addresses, or production changes are included.
