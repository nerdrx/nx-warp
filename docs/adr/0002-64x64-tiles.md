# ADR-0002: Tile size is 64x64 luma

- **Status**: Accepted
- **Date**: 2026-09-04 (design paper draft 1)
- **Source**: paper 1.1, reconciled in 6.2
- **Affects**: `ref/`, `vk/`, `warp/`, `transport/`, `rc/`

## Context

The tile is the unit of everything: one workgroup decodes it, one entry of the reference-tracking
bitmap covers it, one mode and one motion vector describe it, and it is what a loss conceals. Its
size trades per-tile fixed cost against parallelism and foveation granularity.

At 100 Mbit and 72 Hz a stereo frame is about 174 KB, or 75 bytes per 64x64 tile on average. Fixed
per-tile cost therefore has to stay under about 8 bytes, which is what drives the header and entropy
coder design (paper 1.1). Sections 1, 3 and 4 arrived at 64x64 independently, from the header budget,
from the workgroup shape, and from the datagram arithmetic.

| | 32x32 | 64x64 |
|---|---|---|
| Tiles per eye at 2160x2160 | 4624 | 1156 |
| Pixels per lane (64 lanes, 4:2:0) | 24 | 96 |
| Per-tile fixed overhead at 100 Mbit / 72 Hz (avg tile 37 vs 75 bytes) | about 20 percent | about 10 percent |
| Foveation granularity in lens space | finer | acceptable, fovea about 10 tiles wide |
| Intra efficiency (no cross-tile context) | worse | better |

All figures are design estimates from paper 1.1.

## Decision

64x64 luma tiles, fixed per stream, the same grid on every native layer. A 1-bit `tile_size` field in
the stream header allows 32x32 for a future Lite profile and decoders must accept both, since it only
changes the number of block passes per workgroup, but v1 encoders always emit 64.

The tile grid is defined in the lens-space image the renderer produces, after WiVRn's existing
foveated warp if that is enabled, so the codec's per-tile resolution levels stack on top of
render-side foveation rather than replacing it.

## Consequences

- Per-tile fixed cost lands near 10 percent of the payload rather than 20 percent.
- A 64-lane workgroup is properly fed: 96 pixels per lane at 4:2:0 rather than 24.
- Foveation granularity is coarser. The fovea is about 10 tiles wide, which the paper judges
  acceptable; per-tile `res_level` and QP carry the foveation, not the tile grid (ADR-0008).
- One motion vector now covers 4096 pixels instead of 1024, which costs on fast object motion. The
  paper estimates 15 to 25 percent worse than HEVC block motion in the affected tiles, and reserves
  four vectors per tile as a v2 tool bit (paper 1.10, ADR-0005).
- The integer warp's corner-interpolation error grows with tile size: under 1/32 pel at 32 px, under
  1/16 pel at 64 px below 250 deg/s head rotation (paper 2.2). That is inside the 1/16 pel sampling
  grid, so it is accepted.
- Sections 2 and 5 of the paper were written against 32x32 and still carry 32x32 numbers in places.
  Those are superseded by this decision; see the inconsistency note in the paper's section 6.2.

## Alternatives considered

- **32x32.** Doubles fixed overhead for no decode-time gain, since a 64-lane workgroup would be
  underfed at 24 pixels per lane. Kept reserved by a header bit for high-bitrate USB profiles where
  the payload per tile is large enough to carry the overhead.
- **128x128.** Not evaluated in depth in the paper. It would worsen concealment granularity, the
  single-MV problem and the warp's corner-interpolation error, all in the directions that already hurt.
- **Variable tile size within a frame.** Rejected implicitly by design principle 2: the workgroup
  mapping must be trivial, `tile id = (x/64, y/64)` (paper 5.1.2).
